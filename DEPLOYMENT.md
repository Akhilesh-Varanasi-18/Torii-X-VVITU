# Deploying this app

Everything needed to stand up **ToriiMinds × VVITU** on a server. Nothing here is
secret; the secrets come separately, as one file (see §1).

---

## 1. What is NOT in this repository

One file, deliberately excluded by `.gitignore`, and it is the only thing you need
that git will not give you:

### `.env.local` — four variables, all server-side

```bash
MONGODB_URI=...          # MongoDB Atlas connection string (the long one — see §4)
MONGODB_DB=vvitu         # must NOT be 'srkr' — that is a different college's data
MONGODB_COLLECTION=vvitu_registrations
DASHBOARD_PASSCODE=...   # gates every /admin page and /api/admin/* route
```

Ask the project owner for it over a private channel — not email, not a ticket, not
a chat that is archived publicly. On a PaaS (Vercel, Render, Railway, Amplify) do
not upload the file: copy the four values into the platform's own environment
variable settings.

**Optional:** `NEXT_PUBLIC_SITE_URL` (default `https://vvitu.toriiminds.com`) —
affects only the OG/canonical metadata.

Behaviour when they are missing, so you can recognise it:

| Missing | Symptom |
|---|---|
| `MONGODB_URI` | Every database call throws a clear error. The landing page still renders; registration fails. |
| `DASHBOARD_PASSCODE` | The admin panel refuses *all* logins and reports itself unconfigured. It does **not** fall open. That is intentional. |

Nothing else that git ignores is needed: `node_modules/` and `.next/` are both
build output, regenerated by the commands in §2.

## 2. Build and run

Node **≥ 18.17** (developed on v24). npm — `package-lock.json` is committed, so use
`npm ci`, not `npm install`.

```bash
npm ci
npm run build
npm start          # listens on $PORT, default 3000
```

> ⚠️ **Do not run `npm ci --omit=dev`.** `sharp` is a *runtime* dependency — the
> announcement image routes import it on every upload. It is correctly listed under
> `dependencies`, but a trimmed install will still break image uploads at runtime
> with a module-not-found, and only when an admin tries to publish a poster.

The build does **not** touch the database. Every API route is
`dynamic = 'force-dynamic'`, so a build will succeed even with no `MONGODB_URI` —
and then fail at runtime. Do not read a green build as a working database.

---

## 3. First run — no migration step

Indexes are created lazily and idempotently on first access, so an empty Atlas
cluster needs nothing done to it. The database is expected to start empty: every
figure in the admin panel reads zero until registrations arrive. That is correct,
not a broken connection — confirm with `GET /api/register`, which is a live
health check and returns `{"database":"connected","registrations":0}`.

Collections it will create by itself, all prefixed `vvitu_`:
`vvitu_registrations`, `vvitu_announcements`, `vvitu_coding_programs`,
`vvitu_coding_roster`, `vvitu_coding_snapshots`, `vvitu_coding_audit`.

---

## 4. MongoDB Atlas — the two things that actually bite

**a) Network access.** Atlas rejects connections from any IP that is not on the
cluster's allowlist, and the failure looks like a hang or a generic timeout rather
than "you are blocked". Add the server's egress IP under **Atlas → Network Access**
before first deploy. On a platform with dynamic egress IPs you will need either its
documented static-IP add-on or `0.0.0.0/0` — if you use the latter, treat the
database password as the only thing protecting the data and make it a strong one.

**b) `mongodb+srv://` may not resolve.** The SRV form needs a DNS SRV lookup, and
some networks' resolvers refuse those records. The failure is
`querySrv ECONNREFUSED _mongodb._tcp.<cluster>.mongodb.net` **in under 20ms** — that
speed is the tell, because a real network or auth problem takes seconds to time
out. It is DNS, not credentials.

The `MONGODB_URI` you are given is the **seed-list** form, which names the shard
hosts directly and needs no SRV lookup, so it works either way. Atlas shows it
under **Connect → Drivers → "older driver version"**. If your platform's DNS is
healthy, the SRV form is tidier and equivalent.

## 5. Storage, limits, scaling

- **No persistent disk required.** Announcement posters are stored in MongoDB as
  binary, not on the filesystem — deliberately, because most PaaS filesystems are
  read-only and ephemeral per deploy. Do not "fix" this by writing to `public/`.
- **Stateless.** The admin session is a signed cookie compared server-side against
  a hash of the passcode; there is no session store, so you can run several
  instances behind a load balancer with no sticky sessions.
- Two upload routes declare `maxDuration = 30` and guard request bodies at 4 MB.
  If your platform caps request bodies lower than ~4.5 MB, large roster workbooks
  will fail at the edge before the app sees them.

---

## 6. Please check after deploying

1. `GET /api/register` → `{"success":true,"database":"connected"}`
2. `GET /` renders, and the header, hero gallery and Selection Process all appear
3. `GET /api/admin/overview` **without** logging in → **401**. If this returns data,
   stop and escalate: the panel is unprotected.
4. `/admin` → the passcode gate appears; the passcode logs you in
5. `/dashboard` → redirects to `/admin`
6. `/admin` is served with `noindex` — it lists students by name once data exists
   and must never be indexed

---

## 7. Handling note

This app stores student names, roll numbers, college email addresses and mobile
numbers. Everything under `/admin` and `/api/admin/*` is passcode-gated and marked
`noindex` for that reason. Please serve the whole site over HTTPS, do not copy the
production database into a shared or staging environment without the owner's say-so,
and do not paste exported spreadsheets into tickets or chats.
